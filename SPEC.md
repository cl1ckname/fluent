# Язык спецификаций (черновик v2)

## 0. Модель

Индексы типа устроены как параметры generic-типа, только значением параметра
служит **значение**, а не тип. `amount<c>` — это `amount` с зафиксированным
значением индексного параметра `c`.

- Структура **объявляет** индексные параметры словом `bound`.
- Поле связывается с параметрами одним из двух способов:
  - `equals c` — значение поля равно параметру `c`. Тип поля — обычный
    comparable тип, без индексов;
  - `close <e, ...>` — у поля bounded-тип, и его индексные параметры
    замыкаются выражениями `e, ...` (как инстанцирование generic).
- Параметр без `equals` остаётся ghost: во время выполнения его нет,
  он существует только в типе.
- Индекс объекта фиксирован на всё время жизни объекта. Мутация полей
  разрешена, только если она доказуемо сохраняет индекс.

Структуры без `bound` индексов не имеют. Пути к значениям внутри таких
структур (`w.main.currency`, `w.main<c>`) — обычные термы: они отслеживаются по потоку
и версионируются при присваиваниях.

## 1. Форма записи

Спецификации пишутся в doc-комментарии объявления (структуры, поля,
функции) в стиле ACSL: `// @ ...` или `/*@ ... */`. Каждая инструкция
заканчивается `;`. Внутри `/*@ ... */` символ `@` игнорируется, поэтому
строки можно начинать с `@`, как в ACSL.

Основная форма — `// @` с пробелом: gofmt (с Go 1.19) переписывает `//@`
в `// @` в doc-комментариях объявлений верхнего уровня. `//@` тоже
принимается. Блочный комментарий считается спецификацией, если первый
непробельный символ после `/*` — `@`: gofmt переносит `/*@ ... */`
в `/*\n@ ...\n*/`.

```go
// @ bound <c string>;
type amount struct {
    // @ equals c;
    currency string
    value    float64
}

// @ bound <c string>;
type wallet struct {
    // @ close <c>;
    main amount
    // @ close <c>;
    reserve amount
    name string
}

// @ bound <from, to string>;
type rate struct {
    // @ equals from;
    from string
    // @ equals to;
    to string
    k  float64
}

// @ requires a<c> == b<c>;
// @ returns amount<a<c>>;
func (a amount) sum(b amount) amount { ... }
```

## 2. Грамматика

```
// у структуры
bound     := 'bound' '<' pgroup (',' pgroup)* '>' ';'
pgroup    := ident (',' ident)* gotype          // как в Go: <from, to string>

// у поля
equals    := 'equals' ident ';'                 // значение поля ≡ параметр
close     := 'close' '<' term (',' term)* '>' ';'  // инстанцирование типа поля

// у функции / метода
requires  := 'requires' eq ('&&' eq)* ';'
returns   := 'returns' rtype (',' rtype)* ';'
rtype     := gotype [ '<' term (',' term)* '>' ]
           | '_'                                // тип из сигнатуры, без уточнения

eq        := term '==' term
term      := ident access*                      // параметр/receiver, затем путь
           | literal                            // литерал или константа Go
access    := '.' ident                          // поле
           | '<' ident '>'                      // индексный параметр
gotype    := ident | ident '.' ident
```

## 3. `bound` — у структуры

- Не больше одного `bound` на структуру. Порядок параметров задаёт порядок
  аргументов в `T<...>`.
- Тип параметра — любой comparable тип Go. Он разрешается в области
  видимости пакета структуры.

## 4. `equals` / `close` — у поля

- У поля не больше одной аннотации.
- `equals p`: `p` — параметр этой структуры, тип поля идентичен типу `p`.
  Факт: `field(x, f) ≈ idx(x, p)`.
- `close <e1..ek>`: тип поля — bounded-тип с k индексными параметрами, типы `e_i` совпадают
  с их типами. В `e_i` можно использовать параметры этой структуры и
  литералы/константы. Факт: `idx(field(x, f), q_i) ≈ e_i`.
- Один параметр может встречаться в нескольких аннотациях. Это задаёт
  инвариант: например, `main` и `reserve` у wallet в одной валюте.
- Параметр, который не упомянут ни в одном `equals`/`close`, — ошибка
  (скорее всего опечатка). Позже станет warning.
- Каждое `equals`/`close` — инвариант структуры. Он проверяется в composite literal
  и при каждом присваивании поля: `w.main = x` разрешено, только если
  выводится `x<c> ≈ w<c>`.
- Незаданные поля в литерале имеют нулевое значение, и инвариант проверяется
  с ним:

  ```go
  w1 := wallet{main: rub, reserve: rub} // OK: w1<c> ≈ "rub"
  w2 := wallet{main: rub, reserve: usd} // ERROR: "rub" != "usd"
  w3 := wallet{}                        // OK: w3<c> ≈ ""
  w4 := wallet{main: rub}               // ERROR: reserve = amount{}, "rub" != ""
  ```

## 5. Термы и доступ к индексам

- `x.f` — поле `f`, `x<p>` — индексный параметр `p` типа `x`. Пространства
  имён раздельные, поэтому поле и параметр могут называться одинаково.
- Путь можно продолжать: `w.main<c>`, `w.main.currency`.
- `>>` в `amount<a<c>>` лексер разбирает как две закрывающие скобки.
- В `requires` сравниваются **только индексы**. Каждая сторона равенства —
  путь, который заканчивается на `<p>`, или константа, и хотя бы одна
  сторона — индекс. `a.currency == b.currency` и `a<c> == s` (где `s` —
  обычный параметр) — ошибки, нужно писать `a<c> == b<c>`.
  Позже, возможно, разрешим сравнивать неиндексное значение с индексом.
- В `returns` и `close` ограничения нет: `returns amount<c>`, где `c` —
  обычный параметр функции, допустимо.

## 6. `requires` / `returns` — у функции

- `requires` — предусловие, конъюнкция равенств. Проверяется в точке вызова.
- `returns` перечисляет **все** типы результатов, как в сигнатуре.
  `T<e..>` фиксирует индекс результата. Просто `T` означает, что индекс
  неизвестен (свежий терм). Если `returns` нет, все результаты неизвестны.
- `_` на месте типа означает, что тип подставляется по позиции из сигнатуры,
  без уточнения. Он нужен для типов, которые грамматика не выражает
  (`[]byte`, `map[..]..`, `*T`, `func`).
- Тип в `returns` должен совпадать с типом в сигнатуре.
- `returns T<e_1..e_k>` на позиции `i` — это сахар для
  `\result_i<q_j> == e_j`, где `q_j` — параметры `T`.
- Термы в `requires`/`returns` берутся **в момент входа в функцию**.
- Постусловие действует на **каждом** `return`, включая возврат с ошибкой.
  Идиома «при `err != nil` результат не важен» не относится к системе типов:
  раз функция создаёт объект, она обязана его замкнуть. Например,
  `return amount{currency: c}, err`.
- Постусловие проверяется на каждом `return` в теле функции. В точке вызова
  оно даёт факты о результате с подстановкой фактических аргументов.

## 6a. Позиции типа и контейнеры (черновик, не реализовано)

Правило, как у Go-generics: нельзя написать `type entry struct { a Box }`,
параметр типа обязан быть задан. Так же и у нас:

> Bounded-тип в **позиции типа** (поле структуры, элемент среза, массива,
> map или канала, значение за указателем) всегда замкнут. Индекс задан
> параметрами владельца, константами или (для локальных значений) выведен
> в момент создания. Значений без индекса нет, в том числе пустых
> контейнеров: GADT мы не добавляем.

Следствия:

- Поле bounded-типа без `close` — ошибка (как `Box` без `[T]`). Структура,
  которая хранит `amount`, либо объявляет `bound`, либо замыкает поле
  константой.
- Контейнер bounded-типа сам bounded с теми же параметрами: `[]amount`
  означает `[]amount<c>`, то есть все элементы имеют один `c`. Индекс
  контейнера пишется так же: `s<c>`. Указатель — контейнер из одного
  элемента: `p<c>` — индекс `*p`.
- Разнородная коллекция (суммы в разных валютах) выражается только через
  интерфейсы (`[]any`), как и с generics. Упаковка в интерфейс теряет индекс,
  type assertion возвращает значение с неизвестным индексом.

### Откуда берётся индекс контейнера

| создание | индекс |
|---|---|
| параметр функции `xs []amount` | терм входа `xs<c>`, как у любого параметра |
| результат вызова | из `returns []amount<e>`; без `<...>` неизвестен |
| литерал `[]amount{a, b}` | из первого элемента, остальные проверяются |
| пустой литерал, `make(...)`, `var s []amount`, `new(amount)`* | из аннотации `close` на объявлении; без неё неизвестен |
| `append(s, ...)`, `s[a:b]`, конверсия | тот же, что у `s` |

\* `new(amount)` и `make([]amount, n)` создают нулевые элементы, поэтому без
аннотации их индекс — индекс нулевого значения (`""`). С аннотацией
`close <e>` нужно доказать `"" == e`, иначе инвариант нарушен (как с `w4`).
Для `make([]amount, 0, n)` элементов нет, и индекс берётся из аннотации.

Неизвестный индекс — это не ошибка, а свежий терм: `append(s, rub)` к срезу
с неизвестным индексом не докажет `rub<c> == s<c>`, и сообщение подскажет
добавить `close`.

Аннотация локального объявления — то же `close`, что у поля: она
инстанцирует тип переменной. Термы в ней — параметры функции, локальные
переменные и константы:

```go
// @ close <"rub">;
var s []amount

// @ close <a<c>>;
buf := make([]amount, 0, n)
```

### Операции

| операция | правило |
|---|---|
| `s[i]`, `for _, v := range s` | `s[i]<c> == s<c>` |
| `s[i] = x` | требует `x<c> == s<c>` |
| `&s[i]` | `p<c> == s<c>`, стабильно |
| `append(s, x...)` | требует `x<c> == s<c>`, результат `<c> == s<c>` |
| `copy(dst, src)` | требует `dst<c> == src<c>` |
| `m[k] = x`, `ch <- x` | требует `x<c> == m<c>` / `ch<c>` |

Так закрывается дыра с алиасингом: любая запись в адресуемую память
bounded-типа сохраняет индекс по построению.

Замечание: строго для soundness замкнутость нужна только в адресуемых
позициях (поля, элементы срезов и массивов, значения за указателем). Значения
map и элементы каналов неадресуемы, их можно было бы оставить
разнородными. Выбрано единообразное правило, как у generics.

### Грамматика

`gotype` в `returns` расширяется до типов Go с индексами:
`[]amount<c>`, `*amount<c>`, `map[string]amount<c>`, `[4]amount<c>`.

## 7. Семантика проверки

- Состояние — congruence closure над термами: версии переменных (`x#n`),
  `field(t, f)`, `idx(t, p)`, константы. `field` и `idx` — неинтерпретированные
  функции.
- Разные константы различны. Равенство двух разных констант противоречиво,
  такая точка недостижима.
- `x := e` / `x = e`: создаётся новая версия `x`, и `x#n ≈ term(e)`.
- Composite literal `T{...}`: факты из `equals`/`close` для заданных полей; незаданные
  поля получают нулевое значение (оно известно).
- `if e1 == e2 {A} else {B}`: в `A` добавляется `e1 ≈ e2`, в `B` ничего.
- `if e1 != e2 {A} else {B}`: в `B` добавляется `e1 ≈ e2`, в `A` ничего.
  Если `A` всегда завершается (`return`/`panic`), `e1 ≈ e2` действует
  и в коде после `if`. Поэтому после `if err != nil { return ... }` известно
  `err ≈ nil`.
- `&&` в условии даёт конъюнкцию фактов в then-ветке. `||` фактов не даёт.
- На слиянии веток остаются только равенства, верные в обеих ветках.
- Циклы и `switch`/`select`: переменные, которые в них присваиваются, получают
  свежие термы без фактов. Тело (каждая ветка) проверяется один раз от
  состояния до цикла, после цикла известно только то, что было до него
  (консервативно, без fixpoint).
- Внутри функции её `requires` считаются верными.
- Инварианты `equals`/`close` становятся фактами при чтении поля: любое
  значение bounded-типа им удовлетворяет.
- Индекс объекта стабилен всегда. Обычное поле, прочитанное через указатель или
  у переменной, чей адрес взят (явно `&x`, неявно при вызове метода с
  pointer-receiver, или через захват замыканием), каждый раз даёт свежий терм.
- Переприсваивание переменной с взятым адресом — мутация объекта: оно обязано
  сохранять индексы. Обычную переменную можно переприсвоить любым значением.
- Ошибочная мутация (не сохраняющая индекс) после диагностики не применяется,
  чтобы ошибки не шли каскадом. Литерал с нарушенным инвариантом получает
  неизвестные индексы.
- В `a && b` правая часть проверяется с фактами из `a`, в `a || b` — с фактами
  из `!a`.
- Замыкания проверяются как отдельные функции; захваченные переменные неизвестны.
- `goto`: на метке забывается всё, что меняется в функции.
- Функции без контракта (а также вызовы значений-функций и методов интерфейсов)
  возвращают значения с неизвестными индексами.
- Если равенство не выводится, это ошибка.

## 8. Диагностики

| Где | Что |
|---|---|
| спецификация | синтаксис; неизвестный параметр/поле; не-comparable тип параметра; несовпадение типов в `equals`/`close`/`returns`; `close` на поле не bounded-типа; неверная арность `T<...>`; неиспользуемый параметр |
| точка вызова | `cannot prove a4<c> == a3<c> ("usd" vs "rub")` |
| `return` | тело не подтверждает `returns` |
| присваивание поля | мутация не сохраняет индекс / нарушает `equals`/`close` |

## 9. Вне scope v0 / открытые вопросы

- Указатели в общем виде (`*amount<c>` в полях, алиасинг), интерфейсы,
  замыкания. В v0 поддерживаются pointer-receiver'ы и `&T{...}`: `p<c>` —
  индекс объекта, на который указывает `p`. Мутации через указатель
  (`p.currency = ...`, `*p = ...`) подчиняются общему правилу: они разрешены,
  только если доказуемо сохраняют индекс.
- Сочетание с Go-generics (`Box[T]` с полем `T`, у которого есть индексы).
- Полиморфные сигнатуры `func sum<c>(a amount<c>, b amount<c>) amount<c>`
  как альтернатива `requires`/`returns`.
- Межпакетность через `analysis.Fact` (архитектура должна это учитывать).
- LSP-сервер поверх ядра `checker`.
- **Алиасинг** (не решено). Принцип-кандидат: индекс ячейки памяти
  фиксируется при создании и одинаков для всех алиасов, запись его
  сохраняет — как тип ячейки в самом Go (`[]string` не приводится к
  `[]any`). Обсуждалось «неглубокое владение»: локальная переменная без
  взятого адреса принадлежит функции, и в неё можно писать значение с другим
  индексом (сейчас такая запись в поле — ошибка). Отложено до опыта разметки
  реального проекта: новое понятие для пользователей и нетривиально проверять.
- **`<?>`** (синтаксис принят, семантика — черновик): экзистенциальный
  индекс; чтение из `<?>`-позиции даёт свежий жёсткий индекс, сужение — через
  копию в переменную и проверку поля с `equals`. Кандидат: `<?>`-ячейки
  неадресуемы, как значения map.
- **Вариантность** (не решено): можно ли передавать `[]T<c>` туда, где ждут
  `[]T<?>`, и как параметр объявляет, что принимает `<?>`.
- Факты из `switch` (`case "rub":`) — нужны для сужения `<?>`.
- Хранение значения индекса в рантайме (наблюдение, NOTES.md): отдельного
  требования не вводим; нужно только, чтобы подсказка «добавь явную проверку»
  не выдавалась, если значение индекса нигде не хранится.
