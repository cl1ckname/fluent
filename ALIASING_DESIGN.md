# Слой проверки алиасинга и прав доступа

Статус: основа для планирования, обновлено 10 октября 2026.
Не завершённая формальная спецификация и не описание реализованного алгоритма.
Правила переходов в §11 — черновик для обсуждения и проверки на примерах.

Текущий кандидат — counting permissions: источник прав и учёт выданных
читательских токенов. Сепарационная логика служит основой для ресурсов памяти
и локальной проверки вызовов. Ресурсы держат контексты (кадр функции,
вызываемая функция, место хранения), а не имена переменных. Дробное владение
ConSORT — вариант сравнения.

Документ дополняет `SPEC.md`. Его задача — определить направление расширения,
которое позволит безопасно перезаписывать поля, связанные с индексами `bound`,
при наличии указателей и алиасов. Проверка значений индексов, предусловий,
переходов состояний и структурных инвариантов остаётся задачей существующего
слоя уточнений.

## 1. Задача и мотивация

Фиксация индекса на всё время жизни объекта удобна для неизменяемых свойств,
но исключает typestate: состояние существующего объекта должно иметь право
меняться. Требование создавать отдельную Go-структуру для каждого состояния
не соответствует цели проекта.

Пример необходимого поведения:

```go
// @ requires u<s> == StatusActive;
func (u *Account) Inactivate(role string) error {
    if u.Status == StatusInactive {
        return fmt.Errorf("account already deactivated")
    }
    u.Status = StatusInactive
    return nil
}
```

Новый слой должен определить, имеет ли `u` достаточное право на эту запись.
Как после неё изменяются уточнения и проверяются контракты, определяется
слоем уточнений и здесь не проектируется.

Проблема алиасинга: после изменения через один указатель нельзя продолжать
пользоваться устаревшими знаниями через другой указатель на ту же память.

## 2. Принятые принципы

1. Указатели и создание алиасов остаются разрешены в поддерживаемом подмножестве Go.
2. Изменение `bound`-связанных полей возможно при доказанном исключительном
   праве на соответствующую память.
3. Права относятся к памяти, а не к имени переменной или числу указателей.
4. Распределение прав может меняться по ходу программы.
5. Неоднозначность может приводить к консервативному отказу: отсутствие
   доказательства достаточного права означает запрет доступа.
6. Глобальное забывание фактов обо всех объектах после каждой мутации не
   выбирается как основной механизм.
7. Пользователь работает вместе с верификатором: сложный безопасный код может
   требовать упрощения или более явного контракта. Полнота не является целью;
   разрешать больше доказуемого недопустимо.
8. Реализация должна обходиться без внешних SMT/CHC-решателей вроде Z3.
   Алгоритм вывода прав должен быть разработан отдельно; линейность
   ограничений сама по себе ещё не доказывает простоту такого алгоритма.
9. Пользователь не пишет аннотаций прав. Сводки функций выводятся
   автоматически; язык спецификаций по-прежнему содержит только `bound`,
   `equals`/`close`, `requires`/`returns`. Права защищают только зависимые
   поля — поля, от которых зависят индексы. Позже возможны необязательные
   аннотации на стыках модулей, где пользователь явно описывает, утекает ли
   алиас; без них всё должно работать.

## 3. Что дают ресурсы памяти

Для доказанных алиасов можно хранить одно текущее состояние объекта:

```text
Связи указателей: p = ℓ, q = ℓ
Ресурс памяти: ячейка ℓ.Status с текущим содержимым и правами
```

Копирование адреса не создаёт второй ресурс. Запись меняет общее состояние,
поэтому последующее разрешённое чтение через любой известный алиас использует
актуальную информацию. Доли или токены не нужны ради обновления каждого имени.

Права полезны при отдельной проверке функций и передаче доступа между контекстами:

```go
// @ requires b<s> == StatusActive;
func DeactivateAndUse(a, b *Account) {
    a.Status = StatusInactive
    UseActive(b)
}
```

При неизвестной связи a и b нельзя считать их память независимой. Один
возможный контракт требует исключительный ресурс для изменяемой памяти a
и совместимый независимый ресурс для сохраняемого состояния b. При совпадении
этих ячеек вызывающий не может предоставить оба ресурса. Это консервативный
контракт, не единственно возможный: поддержка совпадающих аргументов требует
другого описания поведения.

Наличие разных имён не доказывает непересечения. Нужно различать доказанное
равенство адресов, доказанное непересечение и неизвестную возможность совпадения.

## 4. Основа из сепарационной логики

В классическом исключительном фрагменте `ℓ ↦ v` описывает ячейку, а `P * Q`
— непересекающиеся участки памяти. Правило рамки позволяет проверить операцию
на требуемом участке, сохранив отделённый остаток. Для разделяемых разрешений
совместимость ресурсов задаётся выбранной алгеброй прав.

Предлагаемая проверка вызова:

1. Выделить требуемые ресурсы.
2. Передать их функции.
3. Сохранить совместимый остаток как рамку.
4. Принять ресурсы и информацию выходного контракта.

Одна ячейка не предоставляется как два независимых полных ресурса. Если метод
имеет лишь `requires`, нельзя подразумевать постусловие о новом статусе: нужны
проверенные сведения об эффекте, иначе затронутое состояние неизвестно.

Рекурсивные предикаты, произвольные графы и разделяющая импликация не являются
обязательными для первого прототипа. Изменение значения и его доказательство
по-прежнему относятся к существующему слою уточнений.

## 5. Выбранный кандидат: counting permissions

| Ресурс | Возможности |
|---|---|
| `Source(0)` | Полный доступ: чтение и запись |
| `Source(n)`, `n > 0` | Источник с n выданными правами чтения; запись запрещена |
| `Read` | Один учтённый читательский токен |
| Отсутствие ресурса | Нет разрешённого доступа к отслеживаемой памяти |

Правило выдачи и возврата для одной памяти:

```text
Source(n) ⇔ Source(n + 1) * Read
```

Пример баланса:

```text
Source(0)
Source(1) + Read(q)
Source(2) + Read(q) + Read(r)
Source(1) + Read(r)          // Право q возвращено.
Source(0)                   // Право r возвращено; запись разрешена.
```

Знак `+` здесь означает учёт ресурсов, не дублирование памяти. Токены нельзя
копировать, возвращать дважды или создавать без изменения источника. Передача
меняет получателя токена, но не количество выданных прав. Одни читательские
токены не создают источник.

В модели Bornat et al. источник с долгом n кодируется целым `n >= 0`, а k
читательских прав — отрицательным `-k`. Сложение частично: два источника не
объединяются; источник не может принять больше прав, чем выдал.
**Ноль означает полный ресурс, а не отсутствие доступа.**

Для реализации используются явные варианты состояния ресурса у одного держателя:
`Source(n)`, `Read(k)` при `k >= 1` и отсутствие ресурса `∅`. В формулах
`Read` означает `Read(1)`. Держатель с источником не хранит отдельные токены:
полученный обратно токен сразу гасит долг, `Source(n) * Read ⇒ Source(n − 1)`.

Это учёт прав, а не число физических указателей. Копирование адреса само по
себе не выдаёт токен. Указатель без ресурса может существовать. Источник с
выданными токенами также сохраняет возможность чтения, но не записи.

Потерять ресурс всегда безопасно: потерянный токен лишь уменьшает возможности
чтения, потерянный источник — возможность записи. Небезопасно только создать
ресурс или считать долг погашенным без возврата токена.

## 6. Держатели ресурсов: контексты, а не имена

Ресурсы держат **контексты**:

- кадр текущей функции;
- вызываемая функция на время вызова;
- место хранения, куда ресурс передан надолго: владеющее поле объекта
  (§11.10), контейнер, замыкание, в будущем горутина;
- «неизвестно» — ресурс ушёл туда, откуда его нельзя законно вернуть.

Имена переменных — лишь пути к блоку памяти `ℓ`. Сколько бы алиасов ни было у блока
внутри функции, ресурс на неё у кадра один.

Пример:

```go
q := p
PrintStatus(q)
p.Status = StatusInactive
PrintStatus(q)
```

Если кадр держит `Source(0)` на блок и `p`, `q` доказанно указывают на него:

| Точка | Ресурс кадра | Где токены |
|---|---|---|
| После копирования адреса | `Source(0)` | Нет |
| Во время первого вызова | `Source(1)` | Один у `PrintStatus` |
| После первого вызова | `Source(0)` | Токен вернулся по сводке |
| Запись через `p` | `Source(0)` | Нет; запись разрешена |
| Во время второго вызова | `Source(1)` | Новый токен у `PrintStatus` |
| После второго вызова | `Source(0)` | Нет |

Второе чтение использует актуальное состояние, а не знание до записи.

Внутри одной функции токены между доказанными алиасами не передаются: оба имени
обращаются к ресурсу кадра. Вопрос времени удержания токена возникает только
на границе контекстов, когда токен уходит в вызов, поле, замыкание или
горутину. Временный вызов выдаёт и возвращает токен в пределах одного правила
(§11.4). Удержание после вызова описывается сводкой функции (§7).

Несколько чтений внутри кадра не требуют выдачи токенов: кадр читает своим
ресурсом. Токен выдаётся только при передаче доступа другому контексту.

## 7. Вызовы функций

Go-сигнатуры недостаточно для определения прав после вызова. Нужны проверяемые
сводки ресурсов, происхождения памяти и связей с возвращаемыми ссылками.

| Поведение | Требование к сводке |
|---|---|
| Временное чтение | Получить читательский ресурс и вернуть его |
| Изменение с возвратом доступа | Получить `Source(0)` и вернуть полный источник |
| Удержание чтения после вызова | Указать получателя токена; долг источника остаётся |
| Передача источника | Указать новый контекст, контролирующий источник |
| Возвращаемый алиас | Сохранить связь адреса и передаваемых ресурсов |

Сводки выводятся из тел функций и пользователем не пишутся (§11.8). Для
функций, сводку которых вывести нельзя, действует правило неизвестного вызова
(§11.4): он не возвращает полный источник. Повторяющиеся аргументы не дублируют ресурс.

Контролируемый источник может выдать два права чтения на один объект для двух
получателей. Получатель только одного единичного токена не может клонировать
его. Последовательная передача одного токена — отдельный возможный сценарий.

Сохранение адреса в поле не закрепляет право навсегда. Если ресурс доступен
анализу и возврат законен, его можно собрать. Обязательный метод `Release`
для каждого сохранённого указателя не вводится. Имя метода или исчезновение
переменной не доказывают возврат ресурса.

Хранение токенов в полях, передача наружу и извлечение ещё
требуют проектирования. Эти возможности не подразумеваются реализованными.
Абстрактная форма сводки, используемая в правилах, приведена в §11.4.

## 8. Ветвления

Ветки взаимоисключающие; их ресурсы не складываются. На слиянии доступно только
состояние, обоснованное на каждом достигающем пути.

```go
p := NewActiveAccount()
q := p
if cond {
    q.Inactivate("admin")
} else {
    p.Inactivate("admin")
}
// При проверенных возвратах ресурса полный источник доступен после if.
```

Поскольку ресурс держит кадр, а не имя, обе ветки заканчиваются одинаковым
состоянием `Source(0)` у кадра, и согласовывать нечего.

Сложный случай:

```go
p := NewActiveAccount()
var q *Account
if cond {
    q = p
} else {
    q = NewActiveAccount()
}
```

Нельзя безусловно объединять ресурсы p и q после слияния. Для первой версии
допустим консервативный отказ на доступе, требующем недоказанных прав.
Хранение всех альтернативных отношений алиасинга не обязательно. На слиянии
у `q` нет общего блока на обоих путях, поэтому доступ через `q` к зависимым
полям отклоняется (§11.5).

Правило слияния асимметрично:

- **Удерживаемые токены сливаются по минимуму.** Лишний токен на одном пути
  теряется, а потеря безопасна.
- **Долг источника сливается не меньше максимума.** Меньший счётчик мог бы
  ложно разрешить запись.

Если долг на ветках образован токенами у разных держателей, после слияния
неизвестно, у кого токен, и вернуть его законно нельзя. Такой долг
**фантомный**: источник становится `Frozen` — чтение разрешено, запись
запрещена до конца жизни ресурса в этом контексте. Диагностика записи должна
называть причину: «право чтения могло остаться в `reg` на ветке `then`
(строка N)», а не просто сообщать об отсутствии права.

Завершающиеся пути проверяются отдельно. Циклы и рекурсия требуют согласования
ресурса; повторный вход не создаёт новый источник. Точная таблица слияния
и правило для циклов — в §11.5 и §11.6.

## 9. Counting permissions, ConSORT и отказ от внешних решателей

Дроби сами по себе не признаны проблемой: их можно представлять точными
рациональными числами. Причина смены кандидата — более прямое объяснение
дисциплины: источник, выдача прав чтения, возврат, запись при отсутствии долга.

| Дробное владение | Counting permissions |
|---|---|
| Симметричное разделение доли | Выдача читательских прав от источника |
| Положительную долю можно дробить дальше | Единичный читательский токен не клонируется |
| Полное право — сумма 1 | Полное право — источник без выданных токенов |
| Подбираются величины долей | Учитываются выдача, передача и возврат |

Это смена алгебры ресурса, не подстановка целых чисел в неизменённый ConSORT.
Правила анализа и доказательство корректности нужно адаптировать. Из ConSORT
полезны модульные входные/выходные права и связь доступа с уточнениями.
Полная реализация ConSORT использует Z3 и CHC; этот алгоритм не выбирается.

### Где возникают неизвестные

Поскольку ресурс держит кадр (§6), внутри функции при известных сводках
вызываемых функций неизвестных величин нет. Проверка тела — детерминированное
прямое распространение состояния: состояние на входе, правило операции,
состояние на выходе. Выбирать распределение прав не требуется.

Неизвестные остаются в двух местах:

1. **Сводки функций.** Выводятся снизу вверх по графу вызовов, для рекурсии —
   неподвижной точкой на конечной решётке (§11.8). Интерфейсы и
   значения-функции обрабатываются как неизвестный вызов.
2. **Циклы.** Неподвижная точка на конечной решётке состояний блока (§11.6).
   Конечность обеспечивается расширением растущего долга до `Frozen`.

Главный источник сложности для решателя — не арифметика, а **дизъюнкции**:
разбор случаев «блоки совпадают / различны». Правила их не вводят: возможное
совпадение без доказательства приводит к отказу, а слияние только ослабляет
состояние. Индуктивные предикаты и разделяющая импликация также не вводятся.

Сохранение ресурса необходимо доказать. Малое число алиасов на объект —
гипотеза для проверки на реальном проекте, а не гарантированное свойство.

## 10. Граница между слоями

Слой алиасинга определяет разрешённый доступ и передачу прав. Слой уточнений
проверяет свойства значений и обновляет своё состояние согласно своей семантике.

Интерфейс между ними должен различать:

- доказанный алиас и неопределённую возможность совпадения;
- разрешённое чтение и исключительную запись;
- передачу доступа и потерю доступа;
- восстановление доступа через доказанный алиас.

Потеря доступа должна исключать использование зависимых текущих фактов через
этот алиас. Снимки обычных значений, прочитанных ранее, не являются чтением
текущей памяти. Восстановление доступа не должно восстанавливать старые факты
о памяти, изменённой через другой указатель. Конкретное версионирование и
перенос актуальных уточнений остаются за существующим слоем.

**Главный контракт между слоями: вид возвращённого ресурса определяет, какие
факты переживают вызов.**

| Что получил вызываемый | Что вернул | Факты о текущем содержимом ячейки |
|---|---|---|
| Ничего (рамка) | — | Сохраняются |
| `Read` | `Read` | Сохраняются: пока существует токен, записи не было |
| `Source(0)` | `Source(0)` | Новые версии ячеек блока; известно только то, что дают `ensures`, `returns` и инварианты |
| `Read` или `Source(0)` | Удержал | Текущих фактов нет до законного возврата доступа |

Пока контекст держит `Source(n)` или `Read(k)`, никто другой не держит
`Source(0)` на этот блок, поэтому факты о текущих версиях его ячеек стабильны без
пересчёта. Это заменяет правило `SPEC.md` §7 «поле, прочитанное через указатель,
каждый раз даёт свежий терм» для зависимых полей.

Новое состояние объекта вызывающий узнаёт из `ensures` (`SPEC.md` §6):
условная клауза `ensures err == nil ==> u<s> == StatusInactive` становится
отложенным фактом о новой версии ячеек и срабатывает в ветке, где известно
`err ≈ nil`.

Полный источник разрешает доступ для выбранной категории записи, но не отменяет
проверку `equals`/`close`: составные инварианты проверяются отдельно.

## 11. Правила переходов (черновик)

Правила описывают проверку одной функции при известных сводках вызываемых
функций. Сводки выводятся автоматически (§11.8); запись ниже — их внутреннее
представление, а не синтаксис для пользователя.

### 11.1. Локации, зависимые поля и единица ресурса

- **Локация** `ℓ` — символическое имя блока памяти: объекта по указателю или
  переменной, у которой взят адрес.
- **Зависимое поле** — поле с `equals` или `close`, а также путь через
  `close`-поля, вложенные по значению, к такому полю (`w.main.currency`).
  Только от зависимых полей зависят индексы, поэтому только они защищаются
  правами. Остальные поля читаются и пишутся по правилам `SPEC.md` §7,
  как сейчас: чтение через указатель каждый раз даёт свежий терм.
- **Единица ресурса в первой версии — блок `ℓ` целиком.** Право на `ℓ`
  покрывает все его зависимые поля. Ресурс заводится только для блоков,
  у которых есть зависимые или владеющие поля (§11.10), то есть для структур
  с `bound`, структур с указателями на них и для переменных таких типов
  с взятым адресом. Ресурс дочернего блока — ресурс корня его региона.
- **Ячейка** `c = (ℓ, f)` — конкретный зависимый путь в блоке `ℓ`. Ячейки
  нужны для версий значений (`mem(c)#v`), но не для прав: права на все ячейки
  блока одни.

Дробление ресурса до отдельных зависимых полей или групп полей, связанных
одним инвариантом, отложено до примера из реального кода, где блокировка
целого объекта мешает.

Внутренний указатель (`&p.f`, `&w.main`) указывает внутрь блока `ℓ`. Доступ
через него к зависимому полю требует права на `ℓ`. Так закрывается обход
через `overwrite(&a.currency)`. Запись через внутренний указатель
в независимое поле (`(&w.main).value`) прав не требует.

### 11.2. Состояние анализа

В каждой точке функции состояние — пара `⟨Γ, Σ⟩`:

- `Γ` — состояние слоя уточнений (congruence closure из `SPEC.md` §7),
  дополненное термами адресов и версий ячеек:
  - `loc(p)` — блок, в который в `Γ` доказанно указывает `p` (для внутреннего
    указателя — блок, содержащий поле); не определена, если такого блока нет;
  - `mem(c)#v` — текущее содержимое зависимой ячейки `c` в версии `v`.
- `Σ` — ресурсы кадра: отображение блок → `Source(n, H)`, `Frozen`, `Read(k)`
  или `∅`. `H` — мультимножество долговременных держателей выданных токенов,
  `|H| = n`. Временные держатели (вызываемая функция на время вызова) между
  операторами не появляются: их токены выдаются и возвращаются в одном
  правиле вызова.

Доказанное равенство адресов — равенство в `Γ`. Доказанное непересечение
не хранится отдельно: оно следует из ресурсов. Если кадр держит `Source(0)`
на `ℓ₁` и любой ресурс на `ℓ₂`, то `ℓ₁ ≠ ℓ₂`, иначе один блок был бы
предоставлен дважды. Для двух `Read` непересечение не следует, но оно и не
нужно: ни один из блоков не записывается, и раздельные факты о них не
противоречат возможному совпадению.

Обозначения возможностей:

```text
readable(ℓ) ⇔ Σ(ℓ) ∈ { Source(_, _), Frozen, Read(k ≥ 1) }
writable(ℓ) ⇔ Σ(ℓ) = Source(0, ∅)
```

### 11.3. Операции внутри функции

Правила ниже относятся к доступу к зависимым полям. Доступ к независимым
полям прав не требует. Если `loc(p)` не определена, а операция затрагивает
зависимое поле, это ошибка: «память `p` не определена: возможны разные
объекты на разных путях».

```text
[NEW]     p := &T{…}  |  p := new(T),  у T есть зависимые поля
          ℓ — новый блок
          Γ' = Γ + p#n ≈ ℓ + факты литерала о mem((ℓ,f))#0
          Σ' = Σ + { ℓ ↦ Source(0, ∅) }

[ADDR]    &x, где x — локальная переменная типа с зависимыми полями
          Если у x где-либо в функции берётся адрес (синтаксически), её хранение
          с объявления — блок ℓₓ с Source(0, ∅). Доступ к зависимым полям x
          подчиняется правилам блока ℓₓ, а не версионированию переменной.

[COPY]    q := p  |  q = p
          Γ' = Γ + q#n ≈ p#m
          Σ' = Σ                        // копирование адреса не двигает ресурс

[FADDR]   r := &p.f
          Γ' = Γ + r#n ≈ addr(loc(p), f)
          Σ' = Σ                        // ресурс остаётся у блока

[READ]    x := p.f,  f зависимое,  ℓ = loc(p),  c = (ℓ, f)
          требуется readable(ℓ)
          Γ' = Γ + x#n ≈ mem(c)#v,  v — текущая версия c
          Σ' = Σ

[WRITE]   p.f = e,  f зависимое,  ℓ = loc(p),  c = (ℓ, f)
          требуется writable(ℓ)
          Γ' = Γ + mem(c)#(v+1) ≈ term(e)   // старые снимки в Γ остаются,
                                            // но mem(c)#v больше не текущая
          Σ' = Σ
          + проверка equals/close слоем уточнений

[DEREF]   *r для r ≈ addr(ℓ, f)  — как READ/WRITE для пути f в блоке ℓ
          v := *p   — READ для каждого зависимого поля
          *p = v    — WRITE для каждого зависимого поля
```

`READ` не выдаёт токенов: кадр читает своим ресурсом. Несколько алиасов
одного блока обращаются к одной записи `Σ(ℓ)`.

### 11.4. Вызов функции

Сводка функции выводится автоматически (§11.8) и пользователю не видна
как синтаксис. Её внутренняя форма:

```text
S_f = (Pre, Post, Keep, Fresh)
Pre:   параметр-указатель → Read | Source(0)   // что нужно на входе
Post:  параметр-указатель → Read | Source(0)   // что возвращается вызывающему
Keep:  параметр-указатель → держатель          // что f оставляет себе надолго
Fresh: результаты, возвращаемые со Source(0) на новую память
```

Для каждого параметра из `Pre` должно выполняться одно из двух:
`Post` возвращает ресурс того же или более слабого вида (`Source(0)` → `Read`),
или `Keep` называет держателя. Источник, полученный и не возвращённый,
теряется безопасно: вызывающий получает только чтение и больше не может писать.
Метод с pointer-receiver — функция, у которой receiver является первым параметром.

Вызываемая функция судит о зависимости полей по статическому типу параметра.
Для `p *Account` запись в независимое поле требований не порождает. Для
указателя на не-структуру (`p *string`) функция не знает, куда он указывает,
поэтому любое чтение или запись `*p` попадает в сводку. Вызывающий применяет
требование, только если аргумент указывает в блок с ресурсом: `overwrite(&s)`
для обычной строки `s` прав не требует, `overwrite(&a.currency)` требует
`Source(0)` на блок `a`.

```text
[CALL]    r := f(a₁, …, aₖ)

1. Сопоставление. Для каждого параметра из Pre найти блок вызывающего через
   loc(aᵢ). Если аргумент указывает на память без ресурса, требование
   пропускается. Если loc(aᵢ) не определена, а тип аргумента может указывать
   на зависимые поля, — ошибка.

2. Спрос по блокам. Сложить требования всех параметров, попавших в один блок ℓ:
   - если среди них есть Source(0), он должен быть единственным требованием
     к ℓ, и writable(ℓ); иначе ошибка «одна память передана как изменяемая
     и ещё раз» (случай f(p, p) или f(p, &p.f));
   - если требуется m токенов Read:
       Σ(ℓ) = Source(n, H)  ⇒  выдать m токенов, Σ(ℓ) временно Source(n+m, H)
       Σ(ℓ) = Frozen        ⇒  выдать m токенов (долг уже фантомный)
       Σ(ℓ) = Read(k), k ≥ m ⇒  передать m токенов, Σ(ℓ) временно Read(k−m)
       иначе ошибка «недостаточно прав на чтение ℓ»;
   - Source(0) передаётся целиком: Σ(ℓ) временно ∅.

3. Рамка. Блоки вне спроса не меняются ни в Σ, ни в Γ.

4. Возврат по Post:
   - Read вернулся   ⇒ гасит выданный токен (Source(n+1) ⇒ Source(n))
                        или возвращает переданный (Read(k−1) ⇒ Read(k));
                        версии ячеек ℓ не меняются: пока существовал токен,
                        записи не было;
   - Source(0) вернулся ⇒ Σ(ℓ) = Source(0, ∅); версии всех зависимых ячеек ℓ
                        увеличиваются (новые термы без фактов, кроме
                        ensures/returns/инвариантов).

5. Удержание по Keep:
   - Keep с Read ⇒ токен остаётся у держателя h:
       Source(n+1, H) ⇒ Source(n+1, H + {h});
       Read(k−1) остаётся Read(k−1); при k−1 = 0 блок становится ∅
       и текущих фактов о его ячейках нет;
   - Keep с Source ⇒ Σ(ℓ) = ∅, текущих фактов нет.

6. Fresh. Для каждого результата из Fresh — как [NEW] с новым блоком.
   Результат-указатель без Fresh и без связи с аргументом получает
   неопределённую loc: зависимые поля через него недоступны.
```

Во второй версии держателем в `Keep` может стать путь, из которого токен
можно законно извлечь. В первой версии извлечения нет, поэтому `Source(n > 0)`
между операторами возникает только через `Keep` и необратим. Счётчик долга
окупится с появлением извлечения и конкурентности (§12): ожидание горутины
и `RUnlock` возвращают токены.

**Неизвестный вызов** — функция, для которой сводку нельзя вывести: вызов
через значение-функцию или метод интерфейса, функция без Go-тела (assembly,
`go:linkname`). Если в такой вызов передаётся указатель в блок с ресурсом,
ресурс уходит держателю «неизвестно». Кадр теряет к нему доступ, а при наличии
источника ресурс становится `Frozen` или `∅`. Это отдельная диагностика «память
ушла в вызов, эффект которого неизвестен», а не молчаливый пропуск.

### 11.5. Слияние ветвей

`Γ` сливается по правилам `SPEC.md` §7: остаются равенства, верные на обоих путях.
Если указатель доказанно указывает в разные блоки на разных путях, после
слияния его `loc` не определена. Ячейка, версия которой различается на путях,
получает новую версию без фактов.

`Σ` сливается поблочно. Блок, которого нет на одном из путей, считается `∅`.

| Путь A | Путь B | Слияние |
|---|---|---|
| `Source(n, H)` | `Source(n, H)` | `Source(n, H)` |
| `Source(n₁, H₁)` | `Source(n₂, H₂)`, `H₁ ≠ H₂` | `Frozen` |
| `Source(_)` или `Frozen` | `Frozen` | `Frozen` |
| `Read(k₁)` | `Read(k₂)` | `Read(min(k₁, k₂))` |
| `Source(_)` или `Frozen` | `Read(k)` | `∅` |
| любое | `∅` | `∅` |

Для `Frozen` анализ запоминает причину (ветку и держателя) для диагностики.
Вариант «`Source` против `Read` даёт `∅`» заведомо груб. Его уточнение
не нужно, пока не найдётся реальный код, где пути расходятся так.

Завершающиеся пути (`return`, `panic`) в слиянии не участвуют и проверяются
на выходе (§11.7).

### 11.6. Циклы

1. `Σ₀` — состояние перед циклом.
2. Проверить тело от `Σ₀`, получить `Σ₁` в конце тела и на `continue`.
3. Если `Σ₀ ⊔ Σ₁ = Σ₀`, цикл согласован.
4. Иначе повторить проверку тела от `Σ₀ ⊔ Σ₁`.
5. Расширение: если долг блока растёт между итерациями (`Keep` в теле),
   блок сразу становится `Frozen`.

Решётка состояний блока конечна после расширения, поэтому процесс завершается.
`Γ` по-прежнему обрабатывается как в `SPEC.md` §7: присваиваемые в цикле
переменные получают свежие термы. Поэтому блоки, выделенные в теле, после
итерации недоступны по именам, и их ресурсы фактически теряются (это безопасно).

### 11.7. Выход из функции

На каждом `return` для каждого блока, полученного через параметр:

- если `Post` обещает `Source(0)`, нужно `Σ(ℓ) = Source(0, ∅)`;
- если `Post` обещает `Read`, нужно `readable(ℓ)`; при `Source(n, H)` кадр
  отдаёт вызывающему токен — так функция, получившая источник, может вернуть
  только чтение;
- держатели в `H` и токены, отданные по `Keep` вызываемых функций, должны быть
  перечислены в собственном `Keep` функции;
- `Fresh`-результаты должны указывать на блоки, созданные в функции,
  со `Source(0, ∅)`.

Ресурсы на локальные блоки, не возвращённые и не удержанные, просто
отбрасываются: потеря безопасна.

### 11.8. Вывод сводок

Сводки выводятся только автоматически, синтаксиса для них нет.

- `Pre` для параметра — `Source(0)`, если через него где-либо записывается
  зависимое поле (с учётом `Pre` вызываемых функций), иначе `Read`, если
  зависимое поле читается; иначе параметр не упоминается.
- `Post`, `Keep` и `Fresh` — результат проверки тела от `Pre` по правилам
  §11.3–11.7.
- Обход графа вызовов снизу вверх в пределах пакета. В первой версии
  вызовы других пакетов — встроенные сводки или неизвестный вызов (§13).
  Позже межпакетные сводки будут передаваться через `analysis.Fact`.
- Рекурсия, включая взаимную: неподвижная точка по компоненте сильной
  связности. Начальные сводки пустые; на каждой итерации тела перепроверяются
  с текущими сводками, требования только растут. Решётка для параметра
  конечна (`{нет, Read, Source(0)}` и конечное множество держателей), поэтому
  итерации завершаются. Итоговая сводка проверяется по телам, как и
  нерекурсивная.

**Встроенные сводки.** Часть стандартной библиотеки выводится плохо:
`fmt.Println(acc)` упаковывает указатель в `any` и уходит в `reflect`, что
по правилам — неизвестный вызов. После такого логирования запись в объект
стала бы невозможной. Поэтому верификатор поставляет таблицу встроенных
сводок для частых функций (`fmt`, `log`, `errors`, `strings` и т. п.): как
правило, «`Read` и возврат». Это данные верификатора, а не аннотации
пользователя. Состав таблицы определяется по реальному проекту.

**Объяснимость.** Раз пользователь не видит сводок, диагностика должна
показывать цепочку вывода: «`Inactivate` требует полного права на `u`,
потому что пишет `u.Status` (account.go:31)». LSP может показывать выведенную
сводку при наведении на функцию.

**Цена автовывода — немодульность.** Изменение тела функции меняет её сводку
и может сломать проверку вызывающего кода в другом месте. Диагностика
в вызывающем коде должна указывать на причину в вызываемой функции. Похожий
компромисс в Go уже привычен: escape analysis тоже выводится неявно и
меняется вместе с телом функции.

### 11.9. Разбор примеров

**Совпадающие аргументы.** Для `DeactivateAndUse` из §3 выводится сводка
`Pre: a ↦ Source(0), b ↦ Read`. Вызов `DeactivateAndUse(p, p)`:
блок `ℓ` получает требования `Source(0)` и `Read` → ошибка (§11.4, шаг 2).
Вызов `DeactivateAndUse(p, q)` с разными свежими объектами проходит.

**Условный алиас из §8.** После `if` `loc(q)` не определена: на одном пути
`q ≈ ℓ₁`, на другом `q ≈ ℓ₂`. `q.Inactivate(…)` отклоняется на шаге 1
вызова. `p` по-прежнему имеет `loc(p) = ℓ₁` и `Source(0)`; блок `ℓ₂`
есть только на одном пути и после слияния `∅`.

**Фантомный долг.**

```go
a := NewActiveAccount()   // Fresh: Source(0, ∅)
if cond {
    reg.Track(a)          // Keep: a ↦ Read у reg ⇒ Source(1, {reg})
}
a.Status = StatusInactive // Слияние: Source(1,{reg}) ⊔ Source(0,∅) = Frozen
                          // Ошибка: право чтения могло остаться в reg
                          // на ветке then (строка 3)
```

**Факты через вызов.** При `PrintStatus` со сводкой `Pre/Post: a ↦ Read`
факт `p<s> ≈ StatusActive`, установленный до вызова, остаётся верным после
него. При `Inactivate` со сводкой `Pre/Post: u ↦ Source(0)` версии зависимых
ячеек увеличиваются, и `p<s>` известно только из `ensures` и инвариантов.

**Независимое поле.** `p.value = 10` для `p *amount` прав не требует: `value`
не связано с индексом. Факты о `p.value` по-прежнему не переживают чтения
через указатель (`SPEC.md` §7).

### 11.10. Владеющие поля

**Владеющее поле** — поле-указатель, тип цели которого имеет зависимые или
владеющие поля (`Order.Acc *Account`). Определяется по типу, без аннотаций.
Запись адреса в такое поле блока переносит ресурс цели в этот блок.

**Регион.** Блок, которым владеет поле другого блока, называется дочерним.
Корень вместе со всеми дочерними блоками (транзитивно) образует регион.
Ресурс хранится только у корня: `Σ` содержит записи для корней, а для
дочерних блоков хранится владелец `owner(ℓ) = (ℓ_parent, F)`.

```text
root(ℓ)        = ℓ, если у ℓ нет владельца; иначе root(ℓ_parent)
readable(ℓ)  ⇔ readable(root(ℓ))
writable(ℓ)  ⇔ writable(root(ℓ))
```

Выдача токена или передача `Source(0)` для дочернего блока — это выдача
или передача для корня: пока токен у вызываемой функции, во весь регион
никто не пишет. Это грубее, чем права на отдельные блоки, но не требует
отслеживать подрегионы.

```text
[OWNSTORE] o.F = q  |  &T{F: q},  F владеющее, o (или новый блок) — блок с ресурсом
           требуется writable(o)                  // меняется состав региона
           q = nil ⇒ только отсоединение старого значения
           иначе ℓ_q = loc(q):
             ℓ_q — корень (не дочерний блок), Σ(ℓ_q) = Source(0, ∅);
             ℓ_q ≠ root(o)                         // иначе цикл: ошибка
           старый дочерний блок поля F отсоединяется: его ресурс теряется
           Σ' = Σ − ℓ_q,  owner(ℓ_q) = (loc(o), F)
           версия поля F увеличивается

[OWNLOAD]  p := o.F,  F владеющее
           Если в Γ известно, какой блок лежит в o.F (записан в этой функции),
           loc(p) — этот блок. Иначе заводится символический дочерний блок
           child(loc(o), F)#v для текущей версии v поля F, с owner = (loc(o), F).
           Прав не выдаёт: доступ через p использует права root(o).
```

Запись в поле значения-структуры без адреса (`x := Order{Acc: acc}` для
локальной `x`, у которой адрес не берётся) ресурс не переносит: `x` — не блок,
а `x.Acc` — просто ещё один путь к блоку `acc`. Копия структуры `o2 := *o`
также ничего не переносит: `o2.Acc` указывает в регион `o` и пользуется его
правами.

**Отсоединение при новой версии.** Если ресурс корня возвращается из вызова
как `Source(0)` (§11.4, шаг 4), вызываемая функция могла переставить
владеющие поля. Поэтому все дочерние блоки региона отсоединяются и теряют
ресурс. Повторное чтение `o.F` даёт новый символический дочерний блок.
Указатели, взятые из региона до вызова, после него прав не имеют.

**Сводки.** Параметр, через регион которого что-либо пишется, получает
`Pre: Source(0)`. Перенос блока параметра `a` во владеющее поле параметра `r`
описывается как `Keep: a ↦ owned(r.F)`: у вызывающего `ℓ_a` становится
дочерним блоком региона `r`.

**Что отклоняется.**

```go
o1 := &Order{Acc: acc}
o2 := &Order{Acc: acc}    // ошибка: acc уже принадлежит региону o1
o1.Acc = o2.Acc           // ошибка: переносить можно только корень
a := &Node{}
a.Next = a                // ошибка: цикл, блок требуется дважды
```

Разделяемые ссылки (несколько заказов на один счёт) первой версией не
поддерживаются. Возможное расширение — поле, хранящее токен `Read`:
владельцев несколько, но писать через них нельзя.

**Пример из обсуждения.**

```go
func CloseOrder(o *Order) {
    o.Acc.Status = StatusInactive // OWNLOAD: child(ℓ_o, Acc); writable(root) = writable(ℓ_o)
}                                 // Сводка: o ↦ Source(0) / Source(0)

func main() {
    acc := &Account{Status: StatusActive} // Σ: ℓ_a ↦ Source(0)
    o := &Order{Acc: acc}                 // OWNSTORE: owner(ℓ_a) = (ℓ_o, Acc)
    acc.Status = StatusActive             // разрешено: writable(root(ℓ_a)) = writable(ℓ_o)
    CloseOrder(o)                         // регион ℓ_o: Source(0) отдан и вернулся;
                                          // ℓ_a отсоединён, версия новая
    Charge(acc)                           // ошибка: у acc больше нет прав
    Charge(o.Acc)                         // ошибка: o.Acc<s> неизвестен (новая версия)
}
```

## 12. Расширение на конкурентность

В первой версии конкурентные операции над блоками с ресурсом диагностируются
как неподдерживаемые (§13). Модель выбрана так, чтобы их можно было добавить
новыми правилами по образцу Concurrent Separation Logic, без пересмотра основы.

| Конструкция Go | Ресурсная интерпретация |
|---|---|
| `go f(x)` | Вызов, который не возвращает ресурсы до синхронизации; держатель — горутина |
| `ch <- x` / `<-ch` | Передача ресурса получателю вместе со значением |
| `wg.Wait()` | Возврат ресурсов горутин, связанных с `wg` |
| `sync.Mutex` | Инвариант ресурса блокировки: `Lock` выдаёт `Source(0)`, `Unlock` забирает |
| `sync.RWMutex` | `RLock` выдаёт `Read`, `RUnlock` гасит; `Lock` требует нулевого долга |

Запись требует `Source(0)`, поэтому параллельного читателя или писателя
у записываемого блока нет: отсутствие гонок данных на зависимых полях
следует из той же дисциплины. `RWMutex` почти буквально реализует
counting permissions: источник у мьютекса, токены у читателей.

Связь мьютекса с охраняемыми блоками и `WaitGroup` с горутинами по принципу 9
нужно выводить, а не аннотировать. Возможная основа — вывод связи блокировок
с полями по образцу RacerD. Если вывод окажется ненадёжным, принцип 9 придётся
пересмотреть для конкурентного кода; это решение откладывается до §12.

## 13. Связь с SPEC.md и открытые вопросы

`SPEC.md` пересмотрен под модель прав: §0 (индекс — свойство версии),
§4 (когда запись может менять индекс), §7 (версии содержимого, вызовы по
сводкам), новый §7a (объекты и доступ — пользовательская сторона этого
документа), §8 (диагностики прав), §9. §6a (контейнеры) помечен:
он опирается на неизменный индекс элемента и будет пересмотрен вместе
с контейнерами.

### Решено для первой версии

Первая версия сознательно груба и консервативна: любое уточнение добавляется
только после того, как реальный код покажет, что грубость мешает.

1. **Что защищается правами.** Только зависимые поля — с `equals`/`close`
   и пути к ним через вложенные `close`-поля (§11.1). Независимые поля
   (`amount.value`) читаются и пишутся без прав, по правилам `SPEC.md` §7.
2. **Гранулярность.** Единица ресурса — блок памяти (объект) целиком: право
   на блок покрывает все его зависимые поля. Дробление до отдельных
   зависимых полей или групп полей — после примера из реального кода,
   где блокировка целого объекта мешает.
3. **Аннотаций прав нет.** Сводки только выводятся (§11.8), включая рекурсию
   (неподвижная точка по компоненте связности). Для плохо выводимых функций
   стандартной библиотеки верификатор поставляет встроенные сводки.
4. **Смена индекса только атомарно.** Если индексный параметр связан
   с несколькими полями (`wallet.main` и `wallet.reserve` через `c`), изменить
   его можно только записью объекта целиком (`*w = wallet{...}`) при
   `Source(0)`. Пофилдовая запись по-прежнему обязана сохранять индекс.
   Так инвариант не бывает временно нарушен, и модель упаковки объектов
   (pack/unpack) не нужна.
5. **Чтение зависимого поля без права — ошибка.** Временное решение: нужно
   посмотреть, где это возникает на реальном коде. Альтернатива — свежий терм
   без фактов, корректная до появления конкурентности.
6. **Один пакет.** Сводки выводятся только для функций своего пакета.
   Вызов функции другого пакета — встроенная сводка или неизвестный вызов.
   Межпакетные сводки через `analysis.Fact` — позже.
7. **Владеющие поля** (§11.10). Запись адреса в поле-указатель на сущность
   с зависимыми полями переносит `Source(0)` в регион владельца; права
   региона хранятся у корня. Разделяемые ссылки (несколько владельцев)
   отклоняются. Прочие держатели в `Keep` непрозрачны, извлечения нет;
   удержанный токен необратим (§11.4). Внутри функции вопрос удержания
   снят: ресурс держит кадр (§6).
8. **Слияние.** Таблица §11.5 без уточнений, включая `Source ⊔ Read = ∅`.
9. **Поддерживаемое подмножество Go.** Прямолинейный код, ветвления, циклы
   и вызовы функций с выводимыми сводками. Всё остальное, что затрагивает
   блоки с ресурсом, сводится к одному правилу: ресурс уходит держателю
   «неизвестно» с диагностикой.

   | Конструкция | Поведение в первой версии |
   |---|---|
   | Указатель в блок с ресурсом в срезе, map, канале | Ресурсы уходят «неизвестно» |
   | Метод интерфейса, значение-функция, функция без Go-тела | Неизвестный вызов (§11.4) |
   | Захват указателя или адресуемой переменной замыканием | Ресурсы уходят «неизвестно» |
   | Глобальная переменная-указатель | Запись в неё — уход «неизвестно»; чтение даёт неопределённую `loc` |
   | `go`, `sync`, операции с каналами над блоками с ресурсом | Диагностика «не поддерживается» (§12) |

   Неподдерживаемые операции диагностируются, а не молча пропускаются.
   Это граница применимости, а не доказательство отсутствия гонок.

10. **Обход через указатель на поле** (`overwrite(&a.currency)`) закрыт
   правилами `FADDR`, `DEREF` и §11.4: адрес поля указывает внутрь блока `ℓ`,
   сводка `overwrite` требует `Source(0)` на `p`, вызов проверяет
   `writable(ℓ)`. Для `overwrite(&s)` с обычной строкой `s` прав не нужно. Упаковка указателя в интерфейс
   не создаёт нового права. Копия структуры с указателями или срезами
   не является глубокой копией памяти.

### Отложено

1. **Извлечение из регионов и контейнеры.** Вынос дочернего блока из региона
   обратно в корень (`p := o.Acc; o.Acc = nil`), указатели в срезах и map,
   разделяемые ссылки через поля с `Read`. Зависит от `SPEC.md` §6a.
   Сюда же — сохранение дочерних блоков после вызова: если сводка покажет,
   что функция не переприсваивала владеющий слот (с учётом вложенных путей
   `o.Acc.Sub`), указатели из региона могли бы сохранять права. Пока
   действует отсоединение при новой версии (§11.10): чистота модели важнее.
2. **Конкурентность** (§12). Основа модели под неё готова; правила и вывод
   связей мьютексов и `WaitGroup` — после первой версии. Здесь, возможно,
   придётся пересмотреть отказ от аннотаций (принцип 9).
3. **Состав встроенных сводок** стандартной библиотеки — по реальному проекту.
4. **Уточнения слияния** — по результатам проверки реального проекта.
5. **Необязательные аннотации сводок** для функций вне стандартной
   библиотеки: на стыках модулей пользователь сможет описать, утекает ли
   алиас. Это сахар поверх автовывода, а не замена ему.
6. **Интерфейсы** — после первой версии; до того это неизвестный вызов.
7. **Доказательство сохранения ресурса и оценка сложности.** Ожидаемая
   сложность внутрипроцедурной проверки — линейная по размеру функции,
   умноженная на число итераций циклов, ограниченное высотой решётки блока.
   Это нужно подтвердить вместе с доказательством.

## 14. Основа плана реализации

1. Определить зависимые поля и блоки с ресурсом; описать инвариант источника
   и токенов.
2. Реализовать доказанные локальные алиасы, включая адреса полей, и отделить
   их от неизвестных отношений между ссылками.
3. Реализовать правила §11.3 для прямолинейного кода без вызовов; проверить
   чередование чтение → запись → чтение через алиасы.
4. Добавить правило вызова §11.4 и вывод сводок §11.8: сначала без рекурсии,
   затем неподвижная точка и встроенные сводки; диагностика с цепочкой вывода.
5. Добавить слияние §11.5, циклы §11.6 и консервативный отказ при условном
   алиасинге.
6. Интегрировать версии ячеек со слоем уточнений и диагностикой (§10).
7. Расширять подмножество Go по результатам проверки реального проекта.

### Примеры для проверки будущей реализации

| Ситуация | Ожидаемое требование |
|---|---|
| Запись в свежий объект | Один полный источник доступен |
| Независимые читательские получатели | Токены выданы и долг учтён |
| Чтение через p, затем запись через доказанный алиас q | Разрешено: ресурс у кадра |
| Доступ без ресурса | Отказ |
| Запись при выданном токене | Отказ до законного возврата |
| Повторный возврат токена | Отказ |
| Копирование указателя | Ресурс не дублируется |
| Использование старого текущего факта после передачи/мутации | Недопустимо |
| Несовместимые ресурсы при вызове на одной памяти | Отказ |
| Вызов удерживает токен | Не считать токен возвращённым автоматически |
| Вызов со сводкой Read/Read | Факты о памяти сохраняются |
| Вызов со сводкой Source/Source | Новые версии зависимых ячеек, факты только из контракта |
| Токен удержан на одной ветке | Фантомный долг, запись запрещена, диагностика с причиной |
| Разные долги на выходах | Не уменьшать долг необоснованно |
| Ветки меняют идентичность целевой памяти | Допустим консервативный отказ |
| Право потеряно, имя исчезло | Полное право не возникает само |
| Запись через адрес bound-связанного поля | Проверка той же памяти, без обхода |
| Указатель передан в неизвестный вызов | Ресурсы теряются, диагностика |
| Запись в независимое поле при выданных токенах | Разрешена: права не нужны |
| `fmt.Println(p)` перед записью | Встроенная сводка Read: запись разрешена |
| Взаимная рекурсия читает и пишет объект | Сводка выводится неподвижной точкой |
| Изменение тела меняет сводку | Диагностика у вызывающего указывает причину |
| Цикл повторяет передачу прав | Проверка согласования на обратном ребре |
| Запись через `o.Acc` при правах на `o` | Разрешена: права корня региона |
| Адрес записан во второе владеющее поле | Отказ: блок уже в чужом регионе |
| Указатель из региона после вызова с `Source(0)` | Прав нет: дочерние блоки отсоединены |
