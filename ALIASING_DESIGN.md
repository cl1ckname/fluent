# Слой проверки алиасинга и прав доступа

Статус: итог обсуждения и основа для планирования; не завершённая формальная
спецификация и не описание уже реализованного алгоритма.

Документ дополняет `SPEC.md`. Его задача — определить направление расширения,
которое позволит безопасно перезаписывать поля, связанные с индексами `bound`,
при наличии указателей и алиасов. Проверка значений индексов, предусловий,
переходов состояний и структурных инвариантов остаётся задачей существующего
слоя уточнений.

## 1. Задача и мотивация

Фиксация индекса на всё время жизни объекта удобна для неизменяемых свойств,
но исключает typestate: состояние существующего объекта должно иметь право
меняться. Требование создавать отдельную Go-структуру для каждого состояния
не соответствует цели проекта.

Пример необходимого поведения:

```go
// @ requires u<s> == StatusActive;
func (u *Account) Inactivate(role string) error {
    if u.Status == StatusInactive {
        return fmt.Errorf("account already deactivated")
    }
    u.Status = StatusInactive
    return nil
}
```

Новый слой должен определить, имеет ли `u` достаточное право на эту запись.
Как после неё изменяются уточнения и проверяются контракты, определяется
слоем уточнений и здесь не проектируется.

Проблема алиасинга: после изменения через один указатель нельзя продолжать
пользоваться устаревшими знаниями через другой указатель на ту же память.

## 2. Принятые принципы

1. Указатели и создание алиасов остаются разрешены в поддерживаемом подмножестве Go.
2. Изменение `bound`-связанных полей возможно при доказанном исключительном
   праве на соответствующую память.
3. Права относятся к памяти, а не к имени переменной или числу указателей.
4. Распределение прав может меняться по ходу программы.
5. Неоднозначность может приводить к консервативному отказу: отсутствие
   доказательства достаточного права означает запрет доступа.
6. Глобальное забывание фактов обо всех объектах после каждой мутации не
   выбирается как основной механизм.
7. Пользователь работает вместе с верификатором: сложный безопасный код может
   требовать упрощения или более явного контракта. Полнота не является целью;
   разрешать больше доказуемого недопустимо.
8. Реализация должна обходиться без внешних SMT/CHC-решателей вроде Z3.
   Алгоритм вывода прав должен быть разработан отдельно; линейность
   ограничений сама по себе ещё не доказывает простоту такого алгоритма.

## 3. Заимствуемая идея ConSORT

ConSORT объединяет уточняющие типы с дробным владением. Для ссылки используется
тип `τ ref r`, где `τ` описывает содержимое, а `r` — право доступа.

| Доля | Доступ к соответствующей памяти |
|---|---|
| `r = 1` | Чтение и запись |
| `0 < r < 1` | Чтение |
| `r = 0` | Нет доступа к содержимому и содержательных уточнений о нём |

Права не дублируются при копировании указателя. На одну ячейку суммарно
приходится не более единицы права. Поэтому полный писатель несовместим
с другим читателем, имеющим положительную долю. Физические указатели с нулевой
долей при этом могут продолжать существовать.

Из ConSORT заимствуется механизм прав, а не весь вывод уточнений. В оригинале
ограничения владения решаются через Z3, затем значения долей подставляются в
CHC для вывода уточнений. Это не предлагаемый алгоритм реализации проекта.
Статья называет полную систему владения нелинейной; линейность нашего
ограниченного набора правил должна быть установлена отдельно.

В оригинале операция `alias` позволяет перераспределять права между
известными алиасами. Утверждения об алиасинге являются доверенными: теорема
не исключает `AliasFail`. В проекте планируется разрешать такое
перераспределение только на основании доказанного алиасинга.

## 4. Что означают абсолютные доли

Доли — абсолютные количества права на память. Это не проценты от неизвестной
доли владельца и не счётчик физических ссылок.

```text
p: 1,   q: 0,   r: 0     — запись через p разрешена
p: 1/2, q: 1/4, r: 1/4   — чтение разрешено всем, запись никому
```

Конкретные числа `1/2` и `1/4` не имеют пользовательского смысла:
все положительные неполные доли дают одинаковое право чтения. Числа нужны
для сохранения и объединения ресурса.

Исчезновение имени, выход из области видимости или потеря уточнений не
создают новых прав. В частности, единственный видимый указатель не обязательно
имеет полное право: часть ресурса могла остаться в структуре, контейнере,
замыкании или вызываемой функции.

## 5. Ограничения и их связь между точками программы

Для каждой ссылки в каждой точке анализа возможна своя неизвестная доля.
Строка порождает ограничения; конкретное распределение зависит от связанных
использований программы, а не только от текста этой строки.

Для свежей поддерживаемой ячейки без переданных наружу прав можно начать с `1`.
Имя конструктора само по себе не доказывает свежесть: результат вызова должен
иметь соответствующее проверенное описание происхождения и прав.

Копирование:

```go
p := NewActiveAccount() // Предполагается: возвращает свежий объект и право 1.
q := p                 // p: α, q: β; α + β = 1, α >= 0, β >= 0.
```

Без продолжения кода нельзя выбрать единственные значения `α` и `β`.

Основные ограничения предлагаемой упрощённой модели:

| Событие | Ограничение |
|---|---|
| Граница доли | `0 <= r <= 1` |
| Создание алиаса | `r_original = r_remaining + r_new` |
| Чтение отслеживаемой памяти | `r > 0` |
| Запись, требующая исключительности | `r = 1` |
| Перераспределение между доказанными алиасами | Сумма прав сохраняется |

Система связана между точками программы. Поздняя запись может ограничить
распределение прав после раннего копирования. Это не независимое решение
задачи для каждой строки. Инкрементальный анализ допустим как техника
реализации, если учитывает все зависимости и правила передачи.

## 6. Пример: чтение через p, запись через q

В примерах далее перераспределение в комментариях — внутренний шаг
верификатора, а не принятый синтаксис аннотаций.

```go
p := NewActiveAccount()
q := p
PrintStatus(p)        // Точка A: право p должно быть положительным.
q.Inactivate("admin") // Точка B: право q должно быть полным.
```

Если между A и B права нельзя перераспределять, возникает система:

```text
α + β = 1
α > 0
β = 1
```

Она неразрешима. Сам Go-код не объявляется опасным: выбранная дисциплина
не может проверить его без передачи доступа.

При доказанном `p == q` допускаем передачу:

```go
p := NewActiveAccount() // p: 1.
q := p                 // Одно допустимое решение до чтения: p: 1/2, q: 1/2.
PrintStatus(p)          // p: 1/2, q: 1/2; предполагается возврат прав вызовом.
// Перераспределение: p: 0, q: 1.
q.Inactivate("admin")   // p: 0, q: 1; предполагается возврат полного права.
```

Разные точки получают разные неизвестные:

```text
α₁ + β₁ = 1
α₁ > 0
α₂ + β₂ = α₁ + β₁
β₂ = 1
все доли в [0, 1]
```

Первая пара может быть `1/2 + 1/2` или `1 + 0`; вторая вынужденно `0 + 1`.
Решатель или специализированный алгоритм выбирает числа, но не придумывает
основание для передачи: равенство целевой памяти должно быть доказано.

## 7. Вызовы функций

Go-сигнатуры `func f(a *Account)` недостаточно для определения прав после вызова.
Нужно описание входных и выходных прав, а также их связи с результатами
и памятью, где функция может сохранить доступ.

| Поведение функции | Описание прав |
|---|---|
| Временное чтение | Получает положительную долю и возвращает её |
| Изменение с возвратом доступа | Получает `1` и возвращает `1` |
| Сохранение читающего доступа | Часть ресурса остаётся у получателя сохранённой ссылки |
| Передача исключительного доступа | Вызывающий не получает полное право обратно |

Сохранение адреса и сохранение права — разные события. Сохранённый указатель
с долей `0` не позволяет читать содержимое до последующей законной передачи.

Для функции с доступным телом сведения можно выводить и проверять. Для внешних
функций необходимы явные или заранее проверенные описания. Отсутствие такого
описания не означает автоматический возврат полного права.

Точный формат контрактов, возможность отдельной проверки функции и экспорт
сводок между пакетами ещё не определены. Повторяющиеся аргументы требуют
проверки: вызов `f(p, p)` не может предоставить два независимых права `1`
на одну и ту же память.

## 8. Ветвления

### 8.1. Распределения внутри веток независимы

Ветки взаимоисключающие: их права не складываются. Каждая проверяется
от входного состояния.

```go
p := NewActiveAccount()
q := p

if cond {
    // Вход в ветку: p: 1, q: 0. Передаём право q: p: 0, q: 1.
    q.Inactivate("admin") // p: 0, q: 1.
    // Перед выходом возвращаем право p: p: 1, q: 0.
} else {
    p.Inactivate("admin") // p: 1, q: 0.
}

Use(p) // На обоих достигающих путях: p: 1, q: 0.
```

### 8.2. Согласование на слиянии

После ветвления доступны только права, обоснованные на каждом достигающем
слияния пути. Завершающиеся пути не участвуют в конкретном слиянии, но
проверяются отдельно, включая требования на выходе функции.

Если выходы имеют `p: 0, q: 1` и `p: 1, q: 0`, покомпонентный минимум
потеряет все права. Если `p` и `q` являются доказанными алиасами на обоих
путях, сначала можно согласовать распределение на выходах.

Кандидат алгоритма: группировать общие доказанные алиасы, приводить права
к общей форме внутри групп и затем выполнять консервативное слияние.
Это направление проектирования, а не доказанный полный алгоритм.

### 8.3. Изменение связи между указателями

```go
p := NewActiveAccount()
var q *Account

if cond {
    q = p // q и p указывают на одну ячейку.
} else {
    q = NewActiveAccount() // При контракте свежести — разные ячейки.
}
```

После слияния нельзя безусловно считать `p == q` и объединять их права.
Для первой версии допустимо потерять достаточное право на последующий доступ
и выдать диагностику. Сохранение двух альтернативных состояний или сложного
условного алиасинга не требуется.

Нужно учитывать и возможность совпадения памяти, а не только группы
доказанных алиасов: неизвестные ссылки нельзя автоматически считать разными
и выдавать каждой полное право.

## 9. Линейность и отказ от внешних решателей

Цель — генерировать только линейные ограничения на абсолютные доли при
фиксированной схеме передачи прав. Недопустимо заранее считать, что вся
поддержка Go автоматически укладывается в этот фрагмент.

Примеры решений, которые усложняют задачу:

- Неизвестный процент от неизвестной доли: `transferred = α * r`.
  Вместо этого использовать `transferred + remaining = r`.
- Условный выбор схемы прав в зависимости от неизвестного равенства адресов.
  Это логический выбор между случаями, даже если арифметика каждого линейна.
- Требование точного `min` на слиянии. Для консервативного остатка можно
  использовать `r_join <= r_then` и `r_join <= r_else`, но этого недостаточно
  без согласования идентичности памяти и прав всех связанных ссылок.

Циклы и рекурсивные вызовы требуют согласования состояний; не следует
восстанавливать права простой повторной инициализацией анализа тела.

Необходимо выбрать алгоритм, доказать сохранение ресурса и определить его
сложность. Возможные направления исследования: явное перемещение полного
права внутри групп доказанных алиасов, учёт читающих прав и нормализация
распределений. Конкретный алгоритм пока не выбран.

Доли следует хранить точно, например как рациональные числа или эквивалентное
дискретное представление ресурса, а не сравнивать с единицей через допуск
для floating-point. Замена `r > 0` произвольным фиксированным epsilon
требует обоснования и не является принятым правилом.

## 10. Граница между слоями

Слой алиасинга определяет разрешённый доступ и передачу прав. Слой уточнений
проверяет свойства значений и обновляет своё состояние согласно своей семантике.

Интерфейс между ними должен различать:

- доказанный алиас и неопределённую возможность совпадения;
- разрешённое чтение и исключительную запись;
- передачу доступа и потерю доступа;
- восстановление доступа через доказанный алиас.

Потеря доступа должна исключать использование зависимых текущих фактов через
этот алиас. Снимки обычных значений, прочитанных ранее, не являются чтением
текущей памяти. Восстановление доступа не должно восстанавливать старые факты
о памяти, изменённой через другой указатель. Конкретное версионирование и
перенос актуальных уточнений остаются за существующим слоем.

Полное право необходимо для выбранной категории записи, но не достаточно
для нарушения `equals`/`close`: составные инварианты проверяются отдельно.

## 11. Связь с SPEC.md и открытые вопросы

Перед включением слоя потребуется пересмотреть следующие места `SPEC.md`:

- §0 и §7: утверждение о пожизненной стабильности любого индекса несовместимо
  с изменяемым typestate. Нужно уточнить границы стабильности.
- §4: сохранение индекса при любой записи больше не может быть единственным
  правилом разрешения мутации; структурные связи остаются обязательными.
- §6a: изменение индекса элемента может нарушать замыкание контейнера и
  отношения с другими элементами. Право на один объект не отменяет этих связей.
- §7 и §9: взятие адреса, pointer-receiver, переприсваивание адресуемой
  переменной и захваты должны участвовать в учёте прав.

Решения, ещё не принятые:

1. Гранулярность ресурса: весь объект, отдельное поле или группа полей,
   связанная одним инвариантом. Примеры выше используют право на весь объект.
2. Какие чтения требуют долю и какие записи требуют `1`. Ограниченная защита
   только `bound`-полей должна учитывать все зависимости проверяемых свойств.
3. Автоматическая вставка перераспределений: где, по каким доказательствам
   алиасинга и как выбирается получатель права.
4. Точный алгоритм вывода без внешних решателей и его взаимодействие с CFG.
5. Сводки прав функций: вход, выход, возвращаемые алиасы и сохранённый доступ.
6. Поддерживаемое подмножество Go: циклы, рекурсия, контейнеры, интерфейсы,
   замыкания, глобальная память и конкурентные операции.

Отдельно нужно закрыть обход через указатель на поле:

```go
func overwrite(p *string) { *p = "usd" }
overwrite(&a.currency)
```

Право должно сопровождать доступ к фактической памяти поля, включая передачу
функции с обычным `*string`. Проверять только операции над `*amount`
недостаточно. Упаковка указателя в интерфейс также не создаёт нового права.
Копия структуры с указателями или срезами не является глубокой копией памяти.

До появления правил для escape и конкурентного доступа неподдерживаемые
операции, затрагивающие отслеживаемую память, должны диагностироваться,
а не молча пропускаться. Это граница применимости, а не отдельная задача
доказательства отсутствия гонок в первой версии.

## 12. Основа плана реализации

1. Определить поддерживаемую память и единицу права; описать инвариант ресурса.
2. Реализовать доказанные локальные алиасы, включая адреса полей, и отделить
   их от неизвестных отношений между ссылками.
3. Определить события чтения, записи, копирования, передачи и сохранения доступа.
4. Спроектировать специализированный вывод прав на прямолинейном коде.
5. Добавить проверяемые входные/выходные сводки функций.
6. Добавить согласование веток и консервативный отказ при условном алиасинге.
7. Интегрировать события доступа со слоем уточнений и диагностикой.
8. Расширять подмножество Go по результатам проверки реального проекта.

### Примеры для проверки будущей реализации

| Ситуация | Ожидаемое требование |
|---|---|
| Запись в свежий объект | Полное право доступно |
| Чтение через два алиаса | Обе доли положительные, сумма не больше 1 |
| Чтение через p, затем запись через q | Нужна доказанная передача доступа |
| Доступ через алиас с долей 0 | Отказ |
| Использование старого текущего факта после передачи/мутации | Недопустимо |
| Два изменяющих параметра получают один указатель | Нельзя дублировать право 1 |
| Вызов сохраняет часть прав | Полное право не возвращается автоматически |
| Ветки меняют только распределение известных алиасов | Возможна нормализация перед слиянием |
| Ветки меняют идентичность целевой памяти | Допустим консервативный отказ |
| Право потеряно, имя исчезло | Полное право не возникает само |
| Запись через адрес bound-связанного поля | Проверка той же памяти, без обхода |
| Цикл повторяет передачу прав | Проверка согласования на обратном ребре |
