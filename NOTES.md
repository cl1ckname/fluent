# Заметки по ходу

## Go-инструменты

- **gofmt переписывает `//@` в `// @`** в doc-комментариях объявлений верхнего
  уровня (переформатирование doc comments с Go 1.19). Не трогаются только
  директивы вида `//word:...` и doc-комментарии полей. Решили держаться за `@`:
  основная форма `// @`, `//@` тоже принимается.
- gofmt выравнивает поля структуры по концевым комментариям. Если у поля
  однострочный `/*@ ... */ // коммент`, выравнивание «плывёт». Ни на что не
  влияет, но выглядит некрасиво.
- `go/scanner` не подходит для лексера спецификаций: `a<c>==b<c>` он разбивает
  на `>=` `=`, а `;` в конце строк вставляет сам (пропущенная `;` прошла бы
  молча). Пришлось написать свой небольшой лексер.
- Узлы `go/ast` нельзя расширить, поэтому знания о спецификациях хранятся,
  как в `types.Info`: в отдельных таблицах с ключами-объектами `go/types`
  (`bound.Info`).

## Язык

- В `returns` нужен `_` для типов, которые грамматика не выражает
  (`[]byte`, `*T`, ...): тип подставляется по позиции из сигнатуры.
- `requires` в v0 сравнивает только индексы (`x<p>`) и константы. Это
  сознательное сужение. Кандидат на расширение — сравнение обычного
  значения с индексом (`a<c> == s`).

## Congruence

- `Join` (слияние веток) точный: считается пересечение двух замыканий над всеми
  термами банка. Класс результата — пара (класс в ветке 1, класс в ветке 2).
  Пересечение конгруэнций над множеством, замкнутым по подтермам, — снова
  конгруэнция, поэтому потерь нет. Цена — O(размер банка) на каждое слияние.
  Общая задача join для congruence (Gulwani–Tiwari–Necula) сложнее, потому что
  там результат может требовать бесконечно многих термов. Мы ограничены
  конечным банком, и это сознательное упрощение.
- В противоречивом состоянии (`"rub" ≈ "usd"`) `AreEqual` возвращает true:
  точка недостижима, и в ней выводится всё. В TASK.md было «всегда false»,
  но тогда код внутри `if "usd" == "rub" { ... }` давал бы ложные ошибки.
- `AssertDistinct` нет: про неравенства мы ничего не знаем. Различны только
  разные константы.
