# Прототип: value-indexed types checker для Go

> Рабочая спецификация для первого прототипа. Читать целиком перед началом.
> Цель первого прототипа — **разведка боем**: проверить, что ядро идеи реализуемо
> на реальном Go через `go/analysis`, и нащупать грабли. Это НЕ production-инструмент.

---

## 1. Контекст и идея (зачем всё это)

Мы строим **лёгкую систему индексированных типов** (value-indexed types) поверх Go.
Идея: разрешить программисту помечать некоторые поля структуры как **индексы типа**
(bound-поля), и проверять на этапе анализа, что операции над значениями согласованы
по этим индексам — **без арифметики и без SMT-решателя**, только через
**congruence closure** (проверку равенства термов).

Каноничный пример — деньги: нельзя складывать суммы в разных валютах.

```go
// @bound: currency
type amount struct {
    currency string
    value    float64
}

// @returns: amount[c]
func newAmount(c string, v float64) amount {
    return amount{currency: c, value: v}
}

// @require: a.currency == b.currency
// @returns: amount[a.currency]
func (a amount) sum(b amount) amount {
    return amount{currency: a.currency, value: a.value + b.value}
}

func main() {
    rub := "rub"
    usd := "usd"
    a1 := newAmount(rub, 42)
    a2 := newAmount(rub, 12)
    a3 := a1.sum(a2)   // OK: обе валюты доказуемо "rub"
    a4 := newAmount(usd, 1)
    a5 := a4.sum(a3)   // ERROR: "usd" != "rub", равенство не доказуемо
    _ = a5
}
```

**Ключевые принципы (не нарушать в прототипе):**

- **Только равенства.** Предикаты — это равенства между индексами (`a.currency == b.currency`).
  Никакой арифметики, порядков, неравенств, дизъюнкций. Проверка = congruence closure.
- **Soundness важнее полноты.** Если равенство индексов НЕ доказуемо из известных фактов —
  выдаём ошибку (консервативно). Лучше ложно отвергнуть, чем ложно пропустить.
  Ошибка формулируется как подсказка: "не могу доказать, что валюты равны — добавь явную проверку".
- **bound-поля иммутабельны.** Индекс объекта не меняется после создания. Это снимает проблему
  алиасинга целиком (нельзя тайно поменять индекс через другой указатель). В прототипе:
  считаем bound-поля неизменяемыми и НЕ поддерживаем их мутацию (см. не-цели).

## 2. Что именно проверяем (семантика аннотаций)

Аннотации — это построчные комментарии `// @...` непосредственно перед объявлением.

- `// @bound: <field>` — перед объявлением структуры. Помечает поле как индекс типа.
  Может быть несколько (`@bound: from`, `@bound: to` на разных строках).
  Тип структуры `T` с bound-полями `f1..fk` концептуально становится `T[f1..fk]`.

- `// @require: <eq> [&& <eq>]*` — перед функцией/методом. Предусловие: конъюнкция
  равенств вида `<expr> == <expr>`, где `<expr>` — параметр, `param.field`, или (для метода)
  `recv.field`. Проверяется В ТОЧКЕ ВЫЗОВА.

- `// @returns: T[<expr>, ...]` — перед функцией/методом. Постусловие: индексы результата
  как выражения над параметрами/полями. Используется в точке вызова (чтобы знать индекс
  результата) И проверяется против тела в точке определения (см. §4, это критично для soundness).

Выражения `<expr>` в аннотациях — только: имя параметра, `param.field`, `recv.field`,
строковый литерал. Никаких вызовов, арифметики, индексирования.

## 3. Технологический стек

- Язык реализации: **Go**.
- Фреймворк: **`golang.org/x/tools/go/analysis`** — стандартный способ писать Go-анализаторы.
  Даёт готовый AST (`go/ast`), информацию о типах (`go/types`), и точки для репортинга диагностик.
- Аннотации парсим из `*ast.CommentGroup`, привязанных к декларациям (`ast.CommentMap`
  или обход `Doc` полей у `*ast.FuncDecl` / `*ast.GenDecl`).
- Тесты: `analysistest` (стандартный харнесс для analysis-пакетов — позволяет писать
  ожидаемые диагностики прямо в тестовых `.go` файлах комментариями `// want "..."`).

**Почему go/analysis:** он даёт разрешение имён и типов бесплатно (какая переменная
какого типа, какое поле у структуры), и это ровно та инфраструктура, поверх которой
живут реальные Go-линтеры. Мы хотим на неё опереться, а не парсить Go руками.

## 4. Архитектура (модули)

Разбить на чёткие части, каждая тестируема отдельно:

### 4.1. `annotations` — парсер аннотаций

- Вход: `*ast.File` (или декларации + их doc-комментарии).
- Выход: структуры `BoundSpec{Type string, Fields []string}`,
  `FuncSpec{Name string, Requires []Equality, Returns *IndexExpr}`.
- `Equality{Left, Right IndexExpr}`; `IndexExpr` — одно из: `Param(name)`,
  `FieldAccess(base, field)`, `StringLit(value)`.
- Пиши устойчиво к мусору: незнакомые `@`-теги игнорировать с warning, не падать.

### 4.2. `congruence` — congruence closure / union-find

- **Сердце системы. Реализовать аккуратно и покрыть юнит-тестами в первую очередь.**
- Структуры данных: union-find (disjoint set) над термами.
- Термы: переменные, `field(term, fieldName)` (аппликация «поля» как функции),
  строковые константы.
- API:
  - `MakeSet(term)` / `Find(term)` / `Union(a, b)`
  - `AssertEqual(a, b)` — объединить классы + распространить конгруэнтность
    (если `a≈b`, то `field(a,f) ≈ field(b,f)`).
  - `AreEqual(a, b) bool` — в одном ли классе (это и есть проверка `require`).
  - `AssertDistinct(a, b)` и `AreKnownDistinct(a,b) bool` — для констант:
    разные строковые литералы считаются различными (аксиома различия констант).
    Если запрошено равенство двух known-distinct термов — это противоречие → всегда false.
- Классика: см. алгоритм congruence closure (Nelson–Oppen / Downey–Sethi–Tarjan).
  Для прототипа достаточно простой корректной реализации, не оптимизируй преждевременно.

### 4.3. `index` — модель индексированных типов

- Сопоставление: тип Go (`go/types.Type`) → список его bound-полей (из §4.1).
- Для значения/переменной в программе → его индексные термы (в congruence-домене).
- Функция «индекс выражения»: по `ast.Expr` вернуть congruence-терм его bound-поля.

### 4.4. `checker` — обход тела функции (flow-sensitive dataflow)

- Обходим операторы функции по порядку (прямолинейный dataflow; ветвления — см. ниже).
- Поддерживаем congruence-состояние (факты о равенствах), накопленное к текущей точке.
- На каждом релевантном узле:
  - **Присваивание `x := <expr>`**: связать терм `x` с термом правой части.
  - **Вызов конструктора структуры** `T{f: e, ...}`: для bound-поля `f` установить
    `field(result, f) ≈ term(e)`.
  - **Литерал/константа**: строковый литерал → константный терм; связать переменную с ним.
  - **Вызов функции/метода с `@require`**: для каждого равенства из require —
    проверить `AreEqual` в текущем состоянии. Если НЕ равны (или known-distinct) →
    **диагностика** в точке вызова.
  - **Результат вызова с `@returns`**: приписать переменной-результату индексные термы
    согласно returns-выражению (подставив фактические аргументы).
- **Ветвления (`if`) в прототипе — консервативно:** на слиянии веток, если факт о равенстве
  верен не во всех ветках — сбрасываем его (join = пересечение множеств известных равенств).
  Циклы: для первого прототипа можно обрабатывать тело один раз без fixpoint ИЛИ
  консервативно сбрасывать факты про переменные, изменённые в цикле. Выбери проще, задокументируй.

### 4.5. Проверка `@returns` против тела (в точке ОПРЕДЕЛЕНИЯ) — не забыть!

- **Это критично для soundness.** `@returns: amount[a.currency]` — это обещание.
  Надо проверить, что тело его выполняет: прогнать congruence по телу функции и убедиться,
  что индекс фактически возвращаемого значения `≈` тому, что заявлено в `@returns`.
- Если тело не подтверждает `@returns` → диагностика в точке определения функции.
- Для тел вида «поле результата = поле аргумента» это выводится тем же congruence-обходом.

## 5. Scope первого прототипа (что ДОЛЖНО заработать)

Минимальный работающий результат — прогнать канонический пример из §1 и:

1. Принять `a3 := a1.sum(a2)` без ошибки.
2. Выдать ошибку на `a5 := a4.sum(a3)` с внятным сообщением
   (типа: `cannot prove a4.currency == a3.currency ("usd" vs "rub")`).
3. Проверить `@returns` у `sum` и `newAmount` против их тел (должны пройти).
4. Поддержать пример с `rate.convert` (два bound-поля, `@returns: amount[r.to]`,
   `@require: a.currency == r.from`).

Плюс набор `analysistest`-тестов с `// want`-аннотациями, покрывающих:

- равенство доказуемо (константы совпадают) → нет ошибки;
- равенство недоказуемо (разные константы) → ошибка;
- символические индексы (валюта из параметра): равенство доказуемо, только если
  переменные связаны; иначе — ошибка-подсказка;
- корректный и некорректный `@returns` (тело подтверждает / не подтверждает).

## 6. НЕ-цели (сознательно НЕ делаем в первом прототипе)

Явно откладываем, чтобы прототип не расползся. Если упрёшься — задокументируй как TODO, не реализуй:

- **Арифметика, порядки, неравенства, дизъюнкции в предикатах.** Только равенства.
- **Мутация bound-полей.** Считаем их иммутабельными. Не поддерживаем `p.currency = ...`.
- **Указатели и алиасинг.** Работаем со значениями (value types). Указатели — TODO
  (иммутабельность индексов должна их обезвредить, но это следующий этап).
- **Межпроцедурный вывод `@returns`.** Требуем аннотацию `@returns`, если она нужна;
  вывод из тела — только для тривиальных случаев (поле = поле аргумента), если легко.
- **Циклы с полноценным fixpoint.** Достаточно консервативной обработки.
- **Дженерики Go, интерфейсы, embedding, замыкания.** Только простые структуры,
  функции, методы, вызовы, присваивания, конструкторы, `if`.
- **Красивый вывод / IDE-интеграция / автофиксы.** Достаточно текстовых диагностик.
- **Производительность.** Корректность важнее. Оптимизации union-find — потом.

## 7. Порядок работы (рекомендуемый)

1. Скелет `go/analysis`-анализатора, который просто запускается и ничего не проверяет.
2. `congruence` пакет + юнит-тесты (независимо от Go-специфики). **Начать отсюда — это ядро.**
3. `annotations` парсер + тесты на разбор `@bound`/`@require`/`@returns`.
4. `index` модель: связать go/types с bound-полями.
5. `checker`: обход тела, накопление равенств, проверка `@require` в точке вызова.
6. Проверка `@returns` против тела (§4.5).
7. `analysistest` на каноническом примере (§1) и наборе кейсов (§5).
8. README с примером запуска и списком известных ограничений (перенести сюда не-цели).
